# Aetheris – Phase 11.1: External Knowledge Provider Architecture (Tavily)

You are a Principal AI Systems Architect.

This is NOT a feature request.

This is NOT an architectural redesign.

This is the first implementation of Aetheris' External Knowledge Layer.

The existing architecture is complete and must remain unchanged.

Current Architecture

- FastAPI Backend
- Cognitive Request Router
- Cognitive Reasoning Engine
- Memory Hierarchy
- Session Memory
- Long-Term Memory
- System Memory
- Reflection Engine
- Context Builder
- Prompt Builder
- Memory CRUD
- Memory Persistence
- LLM Provider Layer

Everything currently works correctly.

Do NOT modify any existing functionality.

Do NOT break any APIs.

Do NOT redesign the reasoning engine.

Only extend the architecture by introducing an External Knowledge Provider layer.

---

# Objective

Aetheris must support external knowledge providers.

Tavily will be the first provider.

However,

the Reasoning Engine must NEVER know that Tavily exists.

It should communicate only with an abstract provider interface.

Future providers should be pluggable without changing any reasoning logic.

---

# Design Principles

Implement a provider-based architecture.

Avoid hardcoded integrations.

Follow the same abstraction approach already used for the LLM Provider Layer.

The External Knowledge Layer should be modular and extensible.

---

# Architecture

Create a new module

services/

    external_knowledge/

        __init__.py

        base_provider.py

        provider_manager.py

        tavily_provider.py

---

# Base Provider

Create an abstract base class.

Responsibilities

- Define the common interface for all search providers.
- Do not contain provider-specific logic.
- Support future providers without modification.

Example responsibilities

- search()
- health_check()
- provider_name()

Keep the interface generic.

---

# Tavily Provider

Implement the first concrete provider.

Responsibilities

- Read the API key from environment variables.
- Validate configuration.
- Communicate with Tavily.
- Return normalized search results.

Do not expose Tavily-specific response formats to the rest of the application.

Convert responses into Aetheris' internal format.

---

# Internal Search Result Format

Normalize every provider into a common structure.

Each result should contain

- title
- url
- snippet
- content (if available)
- source
- score (if supported)

Future providers must return the same format.

---

# Provider Manager

Create a Provider Manager.

Responsibilities

- Initialize providers.
- Validate API keys.
- Expose the active provider.
- Allow future provider switching.
- Hide provider implementation details.

The rest of Aetheris should interact only with the Provider Manager.

Never directly instantiate Tavily elsewhere.

---

# Environment Variables

Read

TAVILY_API_KEY

If missing

- log a clear warning
- disable Tavily gracefully
- do not crash the application

---

# Configuration

Centralize provider configuration.

Avoid scattered environment lookups.

Prepare for future providers such as

- Brave Search
- Serper
- Wikipedia
- GitHub
- News APIs

without requiring architectural changes.

---

# Error Handling

Handle

- Missing API key
- Invalid API key
- Network failure
- Timeout
- Empty results
- API rate limits

Return standardized errors.

Never expose raw provider exceptions.

---

# Logging

Log

Provider Initialized

Provider Name

Search Request

Search Duration

Result Count

Provider Errors

Initialization Status

---

# Health Check

Expose a lightweight health check for the provider.

The application should know whether Tavily is currently available.

Failure should not affect the rest of Aetheris.

---

# Constraints

Do NOT modify

- Cognitive Reasoning Engine
- Memory System
- Context Builder
- Prompt Builder
- Reflection Engine
- Existing API routes
- Existing LLM Provider Layer

Do NOT perform searches automatically.

This phase is only responsible for creating the provider architecture.

Search execution will be implemented in the next phase.

---

# Performance

Provider initialization should occur once during application startup.

Avoid repeated initialization.

Use dependency injection where appropriate.

---

# Deliverables

Implement a modular External Knowledge Provider architecture.

Implement Tavily as the first provider.

Normalize all provider responses into a common internal format.

Implement a Provider Manager responsible for provider lifecycle management.

Ensure the rest of Aetheris remains completely unaware of provider-specific implementations.

Maintain full backward compatibility with the existing architecture.

The final result should establish a scalable External Knowledge Layer that allows additional providers to be integrated in the future with minimal effort, while keeping Tavily as the first supported implementation.
